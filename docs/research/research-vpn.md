# Research: per-app VPN options that leave banking apps unaffected

Ticket: #3. Scope: whether a VPN can be scoped on Android so that the DAV client routes through it while excluded apps see **no active VPN at all**, plus per-app routing support in Tailscale / WireGuard / Cloudflare WARP and the work-profile angle.

## Verdict

**Per-app VPN routing is real and cheap** — any app on Android 5.0 (API 21) and later can start a `VpnService` whose tunnel carries only a chosen set of app UIDs, and the two mainstream clients that expose this to a normal user are the official WireGuard app (per-tunnel *Included applications* / *Excluded applications*, min Android 7.0) and Tailscale for Android (*Split tunneling* app picker, min Android 8.0). **But exclusion removes routing, not visibility.** An excluded app still gets the VPN's network from `ConnectivityManager.getAllNetworks()` with `NetworkCapabilities.TRANSPORT_VPN` set, still gets the tunnel interface (and its address) from `NetworkInterface.getNetworkInterfaces()` — which needs no permission at all — and on Android 12+ can additionally request it explicitly with `NetworkRequest.Builder.setIncludeOtherUidNetworks(true)`. So a banking/government app that actually tests for a VPN can still see one; the original objection is **not** defeated by per-app scoping. What per-app scoping *does* buy is that the excluded app's traffic, DNS and routing are untouched by the tunnel.

## 1. Android's own per-app VPN facilities

- `VpnService.Builder` scopes the tunnel to applications, and the two calls are mutually exclusive:
  - `addAllowedApplication(String)` / `addDisallowedApplication(String)` — "Adds an application that's denied access to the VPN connection. By default, all applications are allowed access, except for those denied through this method. **Denied applications will use networking as if the VPN wasn't running.**" A `Builder` may carry an allowlist *or* a denylist, not both ([AOSP `VpnService.Builder#addDisallowedApplication`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/net/VpnService.java); identical text in the published reference [developer.android.com/reference/android/net/VpnService.Builder#addDisallowedApplication(java.lang.String)](https://developer.android.com/reference/android/net/VpnService.Builder#addDisallowedApplication(java.lang.String)) — where the method is marked **Added in API level 21**).
  - Scope is per-UID ranges, not per-interface: `Vpn.java` turns the package lists into UID ranges and attaches them to the VPN network agent's capabilities — `createUserAndRestrictedProfilesRanges(mUserId, allowedApplications, disallowedApplications)` → `addUserToRanges(...)` ("Add all ranges for user skipping UIDs for disallowedApplications") → `capsBuilder.setUids(...)` ([AOSP `services/core/java/com/android/server/connectivity/Vpn.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/connectivity/Vpn.java)).
  - Therefore the VPN network "applies to" a disallowed app only if that app's UID falls in the ranges — `NetworkCapabilities.appliesToUid(uid)` gates it, and the platform picks an app's VPN with the same predicate: `ConnectivityService.getVpnForUid(uid)` → `nai.networkCapabilities.appliesToUid(uid)` ([AOSP `packages/modules/Connectivity/service/src/com/android/server/ConnectivityService.java`](https://android.googlesource.com/platform/packages/modules/Connectivity/+/refs/heads/main/service/src/com/android/server/ConnectivityService.java), and [`core/java/android/net/NetworkCapabilities.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/net/NetworkCapabilities.java)).
- There is no hidden "don't tell apps about this tunnel" switch: the full public `VpnService.Builder` surface (Android 14 revision) is `setSession`, `setConfigureIntent`, `setMtu`, `setHttpProxy`, `addAddress`, `addRoute`, `excludeRoute`, `addDnsServer`, `addSearchDomain`, `allowFamily`, `addAllowedApplication`, `addDisallowedApplication`, `allowBypass`, `setBlocking`, `setUnderlyingNetworks`, `setMetered` ([AOSP `VpnService.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/net/VpnService.java)).
- User-visible always-on surfaces (non-MDM): **Android 7.0 (API 24)** added Always-on VPN to Settings ("Users can also manually set Always on VPN clients that implement `VPNService` methods using Settings > More > VPN. The option to enable Always on VPN from Settings is available only if VPN client targets API level 24"), plus `DevicePolicyManager.setAlwaysOnVpnPackage()` for device/profile owners ([Android 7.0 release notes](https://developer.android.com/about/versions/nougat/android-7.0)). The user-controlled state lives in `Settings.Secure.ALWAYS_ON_VPN_APP`, `ALWAYS_ON_VPN_LOCKDOWN` ("Whether to block networking outside of VPN connections while always-on is set") and `ALWAYS_ON_VPN_LOCKDOWN_WHITELIST` ([AOSP `core/java/android/provider/Settings.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/provider/Settings.java)).
- Per-app *editing* is not a stock user surface: AOSP Settings' VPN app screens (`VpnSettings`, `AppManagementFragment`, `ConfirmLockdownFragment`) manipulate always-on/lockdown through `VpnManager.setAlwaysOnVpnPackageForUser` and show connect/disconnect state; the per-app list itself is chosen programmatically by the VPN app via `VpnService.Builder` ([`packages/apps/Settings/src/com/android/settings/vpn2/`](https://android.googlesource.com/platform/packages/apps/Settings/+/refs/heads/main/src/com/android/settings/vpn2/)). The privileged platform-VPN exclusion list (`Vpn.setAppExclusionList`, used by system IKEv2/platform VPNs) is `@hide` and gated on `NETWORK_SETTINGS` / `NETWORK_STACK` / mainline-network-stack permissions — out of reach for apps and users ([AOSP `core/java/android/net/VpnManager.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/net/VpnManager.java)).

## 2. The crux: what an excluded app can still detect

**Routing and DNS: excluded.** Verified — the tunnel's UID ranges exclude the app, `appliesToUid` fails, so the app's default network stays the underlying network and its capabilities carry no `TRANSPORT_VPN`; the platform's own wording is "Denied applications will use networking as if the VPN wasn't running".

**Presence: still visible.** Three independent channels, none of which the exclusion touches:

1. `ConnectivityManager.getAllNetworks()` — returns **everything** the framework tracks. Current implementation: `enforceAccessPermission()` (ACCESS_NETWORK_STATE, a normal install-time permission) then a copy of every entry of `mNetworkForNetId`, no UID or user filter ([`ConnectivityService#getAllNetworks`](https://android.googlesource.com/platform/packages/modules/Connectivity/+/refs/heads/main/service/src/com/android/server/ConnectivityService.java)). The method is deprecated since API 31 but still implemented the same way in Android 15 and Android 16 trees I read.
2. `ConnectivityManager.getNetworkCapabilities(network)` — also only requires ACCESS_NETWORK_STATE, and nothing redacts the transport: `getNetworkCapabilitiesInternal` → `networkCapabilitiesRestrictedForCallerPermissions` → `createWithLocationInfoSanitizedIfNecessaryWhenParceled`, whose redaction set is `REDACT_FOR_ACCESS_FINE_LOCATION`, `REDACT_FOR_LOCAL_MAC_ADDRESS`, `REDACT_FOR_NETWORK_SETTINGS` (owner UID, underlying networks); the copy constructor copies `mTransportTypes` unchanged ([`NetworkCapabilities`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/net/NetworkCapabilities.java)). `TRANSPORT_VPN` is a public constant (value 4, API 21). So `getAllNetworks()` + `getNetworkCapabilities()` = "is a VPN up?" for any app holding ACCESS_NETWORK_STATE. The same call also yields the VPN's `LinkProperties`, including its interface name (`LinkProperties.getInterfaceName()` is never sanitized — only captive-portal fields are).
3. `NetworkInterface.getNetworkInterfaces()` — needs **no permission** and is not UID-scoped. In bionic, `getifaddrs()` is built from an `RTM_GETADDR` netlink dump; `RTM_GETLINK` (names/flags/MAC) is only attempted when `getuid() < FIRST_APPLICATION_UID` ("SELinux policy only allows RTM_GETLINK messages to be sent by system apps"), and nameless entries are then resolved with `if_indextoname`/`SIOCGIFFLAGS` ([AOSP `libc/bionic/ifaddrs.cpp`, `getifaddrs()`](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/bionic/ifaddrs.cpp)). Java builds the list from that call with no further filtering ([AOSP `ojluni/src/main/java/java/net/NetworkInterface.java`, `getAll()`](https://android.googlesource.com/platform/libcore/+/refs/heads/main/ojluni/src/main/java/java/net/NetworkInterface.java)); the documented restriction is only that non-system apps see "`NetworkInterface`s associated with an `InetAddress`" ([developer.android.com/reference/java/net/NetworkInterface#getNetworkInterfaces()](https://developer.android.com/reference/java/net/NetworkInterface#getNetworkInterfaces())). The tunnel qualifies: it is a real kernel tun device (`/dev/tun`, `IFF_TUN`, name read back with `TUNGETIFF`) and `VpnService.Builder.addAddress` gives it addresses ([AOSP `services/core/jni/com_android_server_connectivity_Vpn.cpp`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/jni/com_android_server_connectivity_Vpn.cpp), [`Vpn.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/connectivity/Vpn.java)). So an excluded app enumerating interfaces sees the tunnel interface — the classic "look for `tun`" detection.
4. Explicit, documented cross-UID asking (Android 12+, API 31): `NetworkRequest.Builder.setIncludeOtherUidNetworks(true)` — "Specifies whether the built request should also match networks that do not apply to the calling UID… the built request will match any network on the system that matches the other parameters" ([developer.android.com/reference/android/net/NetworkRequest.Builder#setIncludeOtherUidNetworks(boolean)](https://developer.android.com/reference/android/net/NetworkRequest.Builder#setIncludeOtherUidNetworks(boolean))). With a `TRANSPORT_VPN` request this tells the app a VPN exists even for networks that deliberately don't apply to it.

Also systemic, though only user-visible: a VPN always shows a system-managed notification and dialog ("A system-managed notification is shown during the lifetime of a VPN connection… A system-managed dialog gives the information of the current VPN connection") ([AOSP `VpnService` class docs](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/net/VpnService.java)).

Consequence for the ticket's premise: exclusion is a **routing** property. "Banking app sees no VPN" requires a **visibility** property that Android does not offer on any version I could find — there is no API, manifest flag, UID-range rule, profile setting or `VpnService` option that suppresses `TRANSPORT_VPN`, suppresses the VPN network in `getAllNetworks()`, or hides the tun interface from a UID.

## 3. Client support in practice

| Client | Per-app routing on a normal (non-MDM) device | How | Version floor |
|---|---|---|---|
| **WireGuard (official Android app)** | Yes | Per-tunnel *Included applications* / *Excluded applications* tabs; the tunnel editor calls `addDisallowedApplication` for `excludedApplications` and `addAllowedApplication` for `includedApplications` ([`GoBackend.java`](https://github.com/WireGuard/wireguard-android/blob/master/tunnel/src/main/java/com/wireguard/android/backend/GoBackend.java), [`TunnelEditorFragment.kt`](https://github.com/WireGuard/wireguard-android/blob/master/ui/src/main/java/com/wireguard/android/fragment/TunnelEditorFragment.kt), [`AppListDialogFragment.kt`](https://github.com/WireGuard/wireguard-android/blob/master/ui/src/main/java/com/wireguard/android/fragment/AppListDialogFragment.kt)) | App `minSdk = 24` (Android 7.0); platform facility needs API 21 |
| **Tailscale (Android)** | Yes, outside a work profile | Settings → *Split tunneling* screen with an app picker and an include/exclude switch; the VPN builder uses the user's `selectedPackageNames()` / `allowSelectedPackages()` when no MDM list is set, and *only* then defers to `MDMSettings.includedPackages` / `excludedPackages` ([`IPNService.kt`](https://github.com/tailscale/tailscale-android/blob/main/android/src/main/java/com/tailscale/ipn/IPNService.kt), [`SplitTunnelAppPickerView.kt`](https://github.com/tailscale/tailscale-android/blob/main/android/src/main/java/com/tailscale/ipn/ui/view/SplitTunnelAppPickerView.kt), [`SplitTunnelAppPickerViewModel.kt`](https://github.com/tailscale/tailscale-android/blob/main/android/src/main/java/com/tailscale/ipn/ui/viewModel/SplitTunnelAppPickerViewModel.kt)) | App `minSdk = 26` (Android 8.0); feature verified in current client source, first shipping release not pinned |
| **Cloudflare WARP / Cloudflare One Client** | **No** | Split Tunnels are route-scoped only: "Split Tunnels can be configured to exclude or include IP addresses or domains from going through the Cloudflare One Client"; mode set per device profile in the Zero Trust dashboard. There is no app/package dimension, and on mobile the rules are applied only when the tunnel starts ([developers.cloudflare.com — Split Tunnels](https://developers.cloudflare.com/cloudflare-one/connections/connect-devices/warp/configure-warp/route-traffic/split-tunnels/)) | n/a |

So the concrete client that delivers "DAV traffic through the tunnel, other apps routed normally" is **WireGuard for Android (7.0+)** or **Tailscale for Android (8.0+)**, on **Android 5.0 (API 21)+** where the platform facility exists.

## 4. Work-profile angle

- **Routing isolation: yes.** A `Vpn` object is bound to one user (`Vpn` constructor takes `userId`, stored as `mUserId`), and its UID ranges are computed with `createUserAndRestrictedProfilesRanges(mUserId, …)`, so a VPN started inside a work profile covers that profile's UIDs (and its restricted profiles), not the personal profile's. Personal apps are therefore not routed through it ([AOSP `Vpn.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/connectivity/Vpn.java)).
- **Visibility isolation: no.** The detection paths in §2 are device-scoped, not profile-scoped: `ConnectivityService.getAllNetworks()` iterates the device-wide `mNetworkForNetId` without any user filter, `getNetworkCapabilities()` only checks ACCESS_NETWORK_STATE, and bionic's `getifaddrs()` filters by nothing but "has an address", never by UID or profile. Personal-profile apps can therefore still observe that a tunnel exists.
- Creating a work profile is itself an enterprise/DPC provisioning flow, so this path does not give a normal user a cheaper option (Android 7.0 release notes describe the profile-owner/DPM model; the settings knobs are `Settings.Secure.ALWAYS_ON_VPN_*`).

## 5. Version floor summary

- Per-app tunnel scoping by a VPN app: **Android 5.0 / API 21** (`addAllowedApplication` / `addDisallowedApplication`).
- Always-on VPN + "Block connections without VPN" user surface: **Android 7.0 / API 24**; `DevicePolicyManager.setAlwaysOnVpnPackage` same level.
- Cross-UID network discovery (`setIncludeOtherUidNetworks`): **Android 12 / API 31** (before that, `getAllNetworks()` already exposed it).
- Detection side: available on **all** these versions — interface enumeration and `getAllNetworks()` predate API 21 (interface enumeration is API 1).

## 6. What is verified vs inferred

Verified from source/documentation: the per-app API and its API level; the UID-range implementation of exclusion; the absence of any hiding API in `VpnService.Builder`; the three detection channels and their permission requirements (AOSP implementations read directly); the deprecation of `getAllNetworks` in API 31 without loss of function; the always-on/lockdown surfaces and their API levels; WireGuard's and Tailscale's per-app code paths and their `minSdk`s; Cloudflare's route-scoped-only Split Tunnels; per-user VPN UID ranges.

Inference (high confidence, not yet exercised on a device): that an excluded app's `NetworkInterface.getNetworkInterfaces()` call actually lists the tun interface on a shipping build. The chain is that exclusion is implemented as per-UID *routing* on one shared tun device (single `establish()` → single fd/interface), while interface enumeration is a netlink address dump filtered only by "has an address" — but a five-minute device test (excluded test app: dump `getNetworkInterfaces()` names + `getAllNetworks()`/`getNetworkCapabilities()` transports with the tunnel up) would turn it from inference into observation. Everything else in §1–§4 is direct.

Not settled by primary sources here: whether a personal-profile VPN and a work-profile VPN can be up simultaneously on a given release (the ticket does not depend on it), and whether any OEM skin adds a per-app editor in Settings — AOSP does not.
